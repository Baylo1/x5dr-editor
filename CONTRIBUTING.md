# Contributing

Thanks for helping. This editor is maintained by one person with one X5DR, so a little process keeps changes safe.

## Reports first

- **Bugs, device reports and feature ideas** go in [GitHub Issues](https://github.com/Baylo1/x5dr-editor/issues/new/choose); pick the matching template. Discussions are off, so Issues is the place for questions too.
- **Device reports** for the X5, X5D and 05R/W are the most useful thing you can send: those models are untested.
- Include **Help → Copy Diagnostics** output with any problem.

## Pull requests

1. **Open an issue first** and agree the change there, before writing code. Unannounced pull requests may be closed.
2. **MIDI changes need a hardware check.** Anything that changes what is sent to or read from the device is verified by the maintainer on a real X5DR before it's merged, so it may take a while.
3. Keep to the project's shape:
   - plain HTML, CSS and JavaScript, with no frameworks and no runtime dependencies;
   - edit `src/` only; `dist/` is generated by `npm run build`;
   - modules use top-level `export function`/`export const` and named relative imports, or the build refuses them (see Landmine #123).
4. Before opening the PR:
   ```bash
   npx vitest run
   npm run build
   ```
   Both must pass; CI runs them on every pull request.
5. Read the relevant entries in `docs/X5DR_Editor_Landmines.md`. Many device behaviours are counter-intuitive, and the Landmines record the ones that have caused regressions. Entries marked **⚑ CONTRACT** must not change behaviour.

## Code style

Match the surrounding code: its naming, comment density and idioms. Unit tests (Vitest) cover the MIDI and data layer; UI changes are checked in the browser.
